# Apps 请求性能与缓存优化方案

> **Status: PARTIALLY IMPLEMENTED** — 部分优化已实施。

## 一、结论

需要优化，但不建议直接按通用清单一次性改完。当前项目已经是 monorepo，且不同 App 的 HTTP 能力不一致：

* `apps/web-blog` 已有相对完整的 HTTP client，包含 timeout、AbortController、拦截器、下载封装、基础错误处理。
* `apps/web-admin` 的 HTTP 封装较薄，主要负责拼 URL、加 Token、处理 401，缺少 timeout、请求取消、请求去重、Trace ID、缓存、重试等能力。
* `packages/` 已经存在多个共享包，适合新增统一 HTTP client package，然后让多个 App 逐步迁移。

因此本轮优化目标应从"单点补丁"调整为：

```text
先统一 HTTP client 基座
再补齐高收益能力
最后逐步迁移各 App
```

## 二、当前现状

### 1. web-blog

`apps/web-blog/src/http/client.ts` 已具备：

* 统一 `createHttpClient`
* `GET / POST / PUT / PATCH / DELETE`
* 下载封装
* 默认 timeout
* `AbortController` 取消请求
* request / response / error interceptor
* JSON / text / blob / arrayBuffer 响应类型
* Token 注入能力

仍缺少：

* Trace ID / Session ID
* GET 请求缓存 TTL
* Stale-While-Revalidate
* in-flight 请求去重
* 条件重试
* 请求耗时日志
* Token 刷新队列

### 2. web-admin

`apps/web-admin/src/http/client.ts` 当前能力较基础：

* 拼接 `BASE_URL`
* 添加 `Authorization`
* 基础 JSON body
* 401 后移除 Token 并跳转登录
* 抛出 `ApiError`

主要缺口：

* 没有 timeout，弱网下可能长期 loading
* 没有外部 `AbortSignal` 支持
* 没有请求去重，页面重复进入或多组件共享接口时容易重复请求
* 没有 Trace ID / Session ID
* 没有缓存策略
* 没有统一拦截器
* 没有条件重试
* 没有请求耗时与失败率日志

### 3. monorepo 结构

当前 `pnpm-workspace.yaml` 已包含：

```text
apps/platform-api
apps/web-admin
apps/web-blog
packages/config
packages/logger
packages/mail
packages/search
packages/honest
```

所以统一能力应优先放在 `packages/http-client`，而不是继续分别堆在 `apps/web-admin` 和 `apps/web-blog` 内。

## 三、优化原则

### 1. 优先统一客户端层，而不是页面内各自处理

性能问题通常不是某个页面单独造成的，而是请求策略分散导致：

* 每个页面自己请求
* 每个页面自己处理 loading / error
* 多组件重复请求同一接口
* 每个 App 的错误处理和 Token 处理不一致

建议建立统一 HTTP client，集中处理：

* timeout
* abort
* Trace ID / Session ID
* cache
* SWR
* retry
* dedupe
* auth
* logging

### 2. GET 优先缓存，写操作主动失效

默认只缓存安全的读请求：

* `GET`
* 明确标记为可缓存的接口

默认不缓存：

* `POST`
* `PUT`
* `PATCH`
* `DELETE`
* 权限敏感接口
* 强实时接口

写操作成功后，应按资源粒度主动失效相关缓存。例如：

```text
更新用户资料成功 -> 失效 user/profile、user/me
发布文章成功 -> 失效 posts/list、posts/detail
修改配置成功 -> 失效 config/*
```

但手动维护 URL 列表容易遗漏。建议设计**缓存标签系统**：每个缓存条目附带标签（如 `user:123`、`post:*`），写操作按标签批量失效，而不是逐个枚举 URL。

### 3. SWR 用于读体验，不用于强一致场景

Stale-While-Revalidate 适合：

* 配置数据
* 公告
* 字典
* 非强实时列表
* 用户资料展示

不适合：

* 支付状态
* 权限判定
* 实时计数
* 强依赖最新状态的后台审批操作

SWR 的准确描述应是：

```text
缓存过期后先展示旧数据，后台刷新新数据，刷新成功后更新缓存和视图。
```

不要表述为"用户永远看到即时数据"，因为用户看到的是可用的旧数据，不一定是最新数据。

### 4. 重试必须按条件判断

可以重试：

| 场景 | 说明 |
| --- | --- |
| 网络错误 | DNS、连接失败、离线恢复 |
| timeout | 可设置较小次数 |
| 5xx | 服务端临时错误 |
| 429 | 需要尊重 `Retry-After` |
| 幂等 GET | 默认可进入重试策略 |

默认不重试：

| 场景 | 原因 |
| --- | --- |
| 400 / 403 / 404 | 客户端或权限问题，重试无意义 |
| 401 | 应走 Token 刷新或登录失效流程 |
| 非幂等 POST / PATCH / PUT | 可能造成重复写入 |

如果业务上明确支持幂等写操作，应通过 `idempotencyKey` 或接口配置单独开启。

### 5. Trace ID 不是安全校验

`Trace ID / Session ID` 的主要作用是：

* 链路追踪
* 排查慢请求
* 排查重复请求
* 关联前端日志和服务端日志
* 统计单会话请求行为

它不能作为"验证请求来源"的安全手段。请求来源验证仍应依赖鉴权、签名、CORS、CSRF 防护、服务端权限校验等机制。

### 6. Abort 应在 composable 层管理，client 层只提供信号

页面卸载、路由切换、重复搜索时应主动取消过期请求，避免：

* 旧请求覆盖新数据
* 页面已卸载仍 set state
* 弱网下无效请求占用连接

但 AbortController 的生命周期应由 composable 层（如 `useRequest`）管理，HTTP client 只负责接收外部 `AbortSignal`。不要在 client 内部自动取消前一个相同 URL 的请求。

| 模块 | 职责 |

## 五、缓存设计

### 1. 缓存 key

缓存 key 至少应包含：

```text
method
url
query
用户身份
语言/区域
租户或站点上下文
权限上下文版本
```

注意：**用户身份应使用 user ID，不要用 token**。token 会变（刷新/过期），用 user ID 避免了 token 刷新后缓存全部丢失的问题。

### 2. 缓存条目结构

SWR 模式下，缓存不能只存 TTL。条目结构应为：

```text
CacheEntry {
  value: T
  cachedAt: timestamp
  ttl: number           // 数据新鲜期，在此期间直接返回
  staleUntil: number    // 数据可用的最大期限，超过后不再返回（即 SWR 的"宽限"时间）
}
```

逻辑：

```text
if now < cachedAt + ttl        → 新鲜，直接返回
if now < cachedAt + staleUntil → 过期但可用（stale），返回旧值 + 后台刷新
else                           → 完全失效，必须请求
```

### 3. 建议 TTL

| 数据类型 | TTL | SWR | 说明 |
| --- | --- | --- | --- |
| 配置数据 | 1-24 小时 | 是 | 变更少，适合缓存 |
| 字典数据 | 1 天 | 是 | 可配合版本号 |
| 公告 / Banner | 10-30 分钟 | 是 | 后台变更后可主动失效 |
| 用户资料展示 | 5-30 分钟 | 是 | 写操作后立即失效 |
| 后台列表页 | 30 秒-5 分钟 | 可选 | 取决于业务实时性 |
| 搜索结果 | 30 秒-2 分钟 | 可选 | query 作为 key |
| 权限 / 登录态 | 不建议长期缓存 | 否 | 以服务端判定为准 |
| 强实时数据 | 不缓存 | 否 | 直接请求 |

### 4. 存储位置

| 存储 | 适合 | 注意 |
| --- | --- | --- |
| Memory | 会话内缓存、敏感数据 | 刷新即丢失 |
| LocalStorage | 小型非敏感配置 | 容量有限、同步阻塞 |
| IndexedDB | 较大结构化缓存 | 实现复杂度较高，且需要处理序列化问题（Date、Map、Set 等会丢失类型） |

第一阶段建议先做 Memory cache，降低风险。确实需要跨刷新保留时，再按接口配置启用 LocalStorage 或 IndexedDB。

### 5. 缓存标签系统

手动维护 URL 列表容易遗漏。建议设计缓存标签系统：

* 每个缓存条目可附带一到多个标签（如 `user:123`、`post:456`、`config`）
* 写操作通过标签批量失效，不用关心具体 URL
* 例如发布文章成功后调用 `cache.invalidateByTag('post:*')`

## 六、请求频率控制

### 1. 请求去重

相同请求正在进行时，后续请求复用同一个 Promise：

```text
GET /user/me 正在请求中
第二次 GET /user/me 直接等待第一次结果
```

要求：

* key 需要包含 URL、query、method、用户上下文
* 成功后释放 in-flight 锁
* 失败后也必须释放 in-flight 锁（否则失败重试会被锁住）
* 对非幂等写请求默认不开启

### 2. 节流与防抖

| 场景 | 策略 |
| --- | --- |
| 搜索输入 | debounce 300-500ms |
| 刷新按钮 | throttle 3-5 秒 |
| 页面初始化公共数据 | dedupe + cache |
| 滚动加载 | throttle 或 IntersectionObserver |
| 自动轮询 | 最小间隔 + 页面不可见时暂停 |

节流和防抖应优先放在调用层或 composable 层；请求层只负责通用 dedupe 和 cache。

## 七、超时、取消与错误处理

### 1. Timeout

建议默认值：

| 类型 | 建议 |
| --- | --- |
| 普通接口 | 8-10 秒 |
| 搜索接口 | 5-8 秒 |
| 上传接口 | 30-60 秒 |
| 下载接口 | 60 秒以上或按业务配置 |

`web-blog` 已有相关能力，应在共享包中沉淀；`web-admin` 应迁移后补齐。

### 2. 统一错误类型

建议统一错误结构：

```text
HttpError
  status
  code
  message
  userMessage
  traceId
  isTimeout
  isNetworkError
  isRetryable
```

页面层只消费标准错误，不直接解析底层 fetch 异常。

### 3. 429 Retry-After

如果遇到 429 限流，应读取 `Retry-After` 响应头，按服务端要求的时间等待后重试，而不是使用默认的指数退避间隔。

## 八、Token 刷新

如果后续使用 Refresh Token，需要避免刷新风暴：

```text
第一个 401 请求触发刷新
其他 401 请求进入等待队列
刷新成功后统一重放
刷新失败后统一登出
```

注意：

* 401 不应进入普通 retry
* 刷新 Token 本身不应再次触发刷新队列
* 刷新失败后要清理队列，避免 Promise 永久 pending
* 登录失效（refresh token 也过期）后应清 Token 并跳转登录

当前 `web-admin` 是 401 后直接清 Token 并跳转登录，可以先保留这个行为；等后端支持 Refresh Token 后再升级。

## 九、日志与观测

前端请求日志建议记录：

* URL 模板或接口名，不记录敏感 query
* method
* status
* duration
* traceId
* sessionId
* cache hit / miss / stale
* retry count
* error code

注意：

* 不记录 Authorization
* 不记录密码、Token、验证码
* 不直接上报完整请求体
* 生产环境按采样率上报

服务端应把 `X-Trace-Id` 写入访问日志，才能真正完成链路追踪。

## 十、CDN 与静态资源

CDN 是部署层优化，和 HTTP client 优化并行推进。

建议：

* JS / CSS / 图片 / 字体走 CDN
* 对带 hash 的构建产物设置长缓存
* `index.html` 设置短缓存或 no-cache
* 开启 Brotli / gzip
* 图片资源使用合适格式和尺寸

CDN + 边缘缓存对海外服务器场景收益很高，但不应阻塞前端请求层治理。

## 十二、推荐迁移路线

### 阶段 1：建立共享包

目标：

* 不改变业务页面行为
* 先提供和当前 `web-blog` HTTP client 接近的能力
* 补齐 `web-admin` 缺失的 timeout / abort / error 能力

验收：

* `packages/http-client` 有单元测试
* 支持 GET / POST / PUT / PATCH / DELETE
* 支持 timeout
* 支持外部 AbortSignal
* 支持标准错误类型
* 支持请求头扩展

### 阶段 2：迁移 web-admin

原因：

* 当前 `web-admin` HTTP client 更薄，收益更明显
* 迁移风险较低

验收：

* 原有接口调用行为不变
* 401 登录失效行为保持一致
* 弱网请求不会无限 loading
* 测试覆盖成功、失败、401、timeout

### 阶段 3：加入去重、Trace、Memory Cache

验收：

* 同一 GET 同时触发只发出一次真实请求
* 请求失败后 dedupe 锁释放，可再次请求
* 每个请求都有 Trace ID
* 同一 Session 内有稳定 Session ID
* 可缓存接口命中缓存时不发起网络请求

### 阶段 4：迁移 web-blog

原因：

* `web-blog` 已有较完整封装，迁移需要注意保持现有下载、拦截器、响应类型能力

验收：

* 下载功能不回退
* interceptor 行为不回退
* timeout 行为不回退
* 现有测试通过

### 阶段 5：部署层优化

目标：

* CDN
* Brotli / gzip
* 静态资源缓存
* 图片资源优化

验收：

* 首屏静态资源从 CDN 命中
* hash 静态资源可长期缓存
* `index.html` 不被错误长缓存
* Brotli 或 gzip 生效

## 十三、风险与边界

### 1. 不要全局默认缓存所有 GET

部分 GET 可能依赖权限、时间、服务端状态。应通过接口配置显式启用缓存，或者按白名单启用。

### 2. 不要把 Trace ID 当安全能力

Trace ID 可伪造，只能用于观测，不用于鉴权。

### 3. 不要简单合并接口

页面初始化请求多，不代表一定要合并接口。HTTP/2 多路复用、缓存、去重、延迟加载通常更稳。只有当多个接口强绑定且总是一起使用时，才考虑后端聚合接口。

### 4. 不要对写操作做无条件重试

非幂等写请求重试可能造成重复提交。需要业务幂等键或明确接口语义。

### 5. 不要在本地长期保存敏感数据

用户资料、权限、Token 相关数据要谨慎缓存。跨刷新持久化缓存需要评估安全和过期策略。

### 6. 缓存 value 序列化问题

Memory cache 保存 JavaScript 对象引用是安全的。但如果使用 IndexedDB 持久化，需要处理序列化/反序列化——Date 会变成字符串、Map/Set 不可直接存储、循环引用会报错。建议定义 `CacheSerializer` 接口，各存储层各自实现。

## 十四、预期收益

| 优化项 | 预期收益 |
| --- | --- |
| timeout / abort | 减少长期 loading 和旧请求覆盖 |
| 请求去重 | 降低重复请求，减少请求风暴 |
| TTL cache | 降低稳定数据重复请求 |
| SWR | 弱网下提升可感知速度 |
| Trace ID | 提升排障效率 |
| 统一错误处理 | 降低页面重复逻辑 |
| 共享 HTTP client | 降低两个前端 App 的维护成本 |
| CDN / 压缩 | 提升静态资源加载速度 |

## 十五、建议最终排序

推荐按下面顺序执行：

```text
1. packages/http-client 基础能力
2. web-admin 迁移
3. Trace ID / Session ID
4. GET 请求去重
5. Memory TTL cache
6. SWR + 主动失效 + 缓存标签系统
7. 条件 retry（含 429 Retry-After）
8. web-blog 迁移
9. CDN / 压缩 / 静态资源缓存
10. Token 刷新队列与监控平台
```

这个顺序能先解决最确定的问题，同时避免把缓存、重试、Token 刷新、CDN 混成一个高风险大改。
