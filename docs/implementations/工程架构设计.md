# Monorepo 工程架构设计说明（Turborepo + Changesets + Lefthook + Biome）

> **Status: REFERENCE** — Monorepo 工程架构设计参考文档。

## 1. 目标

本仓库采用 monorepo 结构，统一管理多个应用（apps）与可发布模块（packages），目标如下：

- 统一代码管理与依赖版本控制
- 支持模块级独立发布（npm）
- 提供高效构建与缓存能力
- 保证代码质量与提交规范
- 自动化发布流程，减少人为操作成本

## 2. 项目结构设计

```txt
repo/
  apps/                      # 运行应用（不发布）
    platform-api/
    web-blog/

  packages/                 # 可复用模块（部分发布到 npm）
    core/                   # @rx-ted/packages-core
    honest/                 # @rx-ted/packages-honest
    honest-plugins/         # @rx-ted/packages-honest-plugins (barrel)
      db/
      cache/
      mail/
      s3/
      api-doc/

  .changeset/               # 版本变更记录
  .github/workflows/        # CI/CD
  CHANGELOG.md              # 版本日志
```

## 3. 核心设计原则

### 3.1 apps vs packages 分离原则

| 类型     | 是否发布 npm | 职责         |
| -------- | ------------ | ------------ |
| apps     | ❌ 不发布    | 业务运行服务 |
| packages | ✔ 发布       | 可复用模块   |

**设计原因：**

- apps 属于运行时产物，不需要版本化
- packages 是跨项目复用单元，需要独立版本控制

### 3.2 单向依赖原则

```txt
apps → packages ✔
packages → packages ✔
packages → apps ❌（禁止）
```

**目的：**

避免依赖循环与发布污染，使模块具备独立性与可发布性。

## 4. 工具选型与职责划分

Turborepo构建与任务调度

### 职责

- 管理 monorepo 任务执行
- 提供缓存机制（build/test/lint）
- 处理依赖 DAG（任务依赖图）

### 解决的问题

- 多项目重复构建问题
- 构建速度慢
- 任务顺序复杂

### 示例能力

```bash
pnpm turbo run build
```

自动执行多个项目构建

## 设计定位

> ❗ Turborepo 只负责“运行效率”，不负责版本与发布

Changesets（版本与发布系统）

### 职责

- 管理版本变更（semantic versioning）
- 生成 changelog
- 控制 npm publish 流程

### 核心能力

每次修改 packages 后：

```bash
pnpm changeset
```

生成：

```md
---
"@rx-ted/core": minor
---

fix feature
```

---

## 解决的问题

### 1. 版本混乱问题

- 不同 package 自动独立 version

### 2. 发布不可追踪问题

- 每次发布有 changelog 记录

### 3. 人工 npm publish 风险

- 自动化发布流程

## 发布机制

CI 自动执行：

```txt
changeset version → bump package.json
changeset publish → npm publish
```

---

## 设计定位

> ❗ Changesets 是“版本与发布控制中心”

---

# 4.3 Lefthook（提交约束工具）

## 职责

- Git hooks 管理
- 提交前校验

## 主要用途

### pre-commit

```bash
pnpm biome check .
```

### commit-msg

```bash
pnpm changeset status
```

---

## 解决的问题

- 防止未 lint 代码提交
- 防止忘记 changeset
- 保证提交质量一致

---

## 设计定位

> ❗ Lefthook 是“本地质量守门员”

---

# 4.4 Biome（代码规范工具）

## 职责

- 代码格式化
- 静态检查（lint）

## 替代方案

- ESLint + Prettier（传统）
- Biome（统一替代方案）

---

## 解决的问题

- 统一代码风格
- 减少 CI lint 成本
- 提升开发速度

---

## 设计定位

> ❗ Biome 是“代码质量基础设施”

---

# 5. 发布系统设计（核心）

## 5.1 发布触发机制

仅允许 CI 发布：

```
push main / merge PR
```

---

## 5.2 发布流程

```
1. detect changeset
2. version bump
3. build (turbo)
4. publish npm (@rx-ted/*)
```

---

## 5.3 发布规则

| 行为              | 是否允许     |
| ----------------- | ------------ |
| 本地 npm publish  | ❌ 禁止      |
| CI publish        | ✔ 允许       |
| 自动 version bump | ✔ Changesets |

---

## 6. 版本管理策略

采用：

> Independent Versioning（独立版本策略）

### 示例

```
@rx-ted/core@1.2.3
@rx-ted/ui@2.0.1
@rx-ted/utils@0.9.5
```

---

## 优点

- 每个 package 独立演进
- 避免无意义全量 bump
- 更符合模块化架构

---

## 7. 依赖管理策略

### workspace 模式

开发阶段：

```json
{
  "dependencies": {
    "@rx-ted/core": "workspace:*"
  }
}
```

发布后：

```
workspace:* → npm version 自动替换
```

## 9. 架构问题解决总结

| 问题              | 解决方案                |
| ----------------- | ----------------------- |
| 多项目构建慢      | Turborepo cache         |
| 版本混乱          | Changesets              |
| 手动发布风险      | CI publish              |
| 提交质量不一致    | Lefthook                |
| 代码风格不统一    | Biome                   |
| packages 复用困难 | workspace + npm publish |

## 10. 最终架构定位

本系统本质是一个：

> **“模块化可发布 monorepo 工程体系”**

其能力分层如下：

```
┌────────────────────────────┐
│        CI/CD (GitHub)      │
│  release / publish / bump  │
└────────────┬───────────────┘
             │
┌────────────▼───────────────┐
│       Changesets           │
│ versioning + changelog     │
└────────────┬───────────────┘
             │
┌────────────▼───────────────┐
│       Turborepo            │
│ build / cache / pipeline   │
└────────────┬───────────────┘
             │
┌────────────▼───────────────┐
│ Lefthook + Biome           │
│ quality + formatting       │
└────────────┬───────────────┘
             │
      apps / packages
```
