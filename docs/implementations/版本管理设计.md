# 版本管理与变更日志模块设计方案（V2）

> **Status: IMPLEMENTED** — 版本管理模块已在 platform-api 中实现。

## Purpose

将版本管理（Version Management）和变更日志（Changelog）设计为独立、自治的业务模块，脱离对 Git Tag 和 Changeset 的强依赖，使其能独立服务于 Web、App、桌面端、API 等多平台场景。

## 核心理念

### 层级版本模型

```
project v0.1.0          ← 根目录 package.json
├── packages/auth       v0.0.1  ← 独立 bump → npm publish
├── packages/honest     v1.2.0  ← 独立 bump → npm publish
├── apps/web-blog       v0.0.1  ← 独立 bump → 不发布
├── apps/web-admin      v0.0.5  ← 独立 bump → 不发布
└── docs                        ← 仅记录 changelog，不 bump
```

### 模块分类

| 分类 | 对 project version 的影响 | 行为 |
|------|--------------------------|------|
| `apps/*` | ✅ 计入 aggregate | 独立 bump，不发布 |
| `docs/`, 根目录文件 | ✅ 计入 aggregate | 记录 changelog，不 bump |
| `packages/*` | ❌ 不计入 aggregate | 独立 bump，npm publish |

**理由**：`packages/auth v2.0.0` 不代表整个项目是 v2.0.0。Project version 只反映面向用户的应用和文档变更。

## 数据模型

### 表关系

```
versions (project 级别)
  │
  ├── module_versions (各模块版本记录)
  │     ├── changelog_entries (按 type 分组的展示内容)
  │     └── commit_records (原始 git commit)
  │
  └── releases (各平台发布)
```

### Table: `versions`

项目级别版本记录。

```sql
CREATE TABLE versions (
  id                    CHAR(36) PRIMARY KEY,
  version               VARCHAR(20) NOT NULL UNIQUE,
  title                 VARCHAR(200) NOT NULL,
  release_channel       ENUM('stable','beta','canary','rc') NOT NULL DEFAULT 'stable',
  status                ENUM('draft','reviewing','approved','releasing','released','rollback','archived') NOT NULL DEFAULT 'draft',
  summary               TEXT,

  min_client_version    VARCHAR(20),
  force_upgrade         BOOLEAN DEFAULT FALSE,
  upgrade_url           JSON,

  rollback_version_id   CHAR(36),                     -- 回滚到哪个版本

  commit_short_hash     VARCHAR(9),                   -- 创建时的 HEAD hash
  commit_url            VARCHAR(500),
  author                VARCHAR(100),
  released_at           DATETIME,
  created_at            DATETIME NOT NULL,
  updated_at            DATETIME NOT NULL,

  INDEX idx_version (version),
  INDEX idx_channel (release_channel),
  INDEX idx_status (status),
  INDEX idx_released_at (released_at)
);
```

### Table: `module_versions`

每个版本中各模块的独立版本记录。

```sql
CREATE TABLE module_versions (
  id                CHAR(36) PRIMARY KEY,
  version_id        CHAR(36) NOT NULL,                -- FK → versions.id
  module_name       VARCHAR(100) NOT NULL,             -- web-blog / auth / honest
  module_type       ENUM('package','app','root') NOT NULL,

  current_version   VARCHAR(20) NOT NULL,             -- 变更前版本
  next_version      VARCHAR(20) NOT NULL,             -- 变更后版本
  bump_type         ENUM('major','minor','patch','none') NOT NULL DEFAULT 'none',

  created_at        DATETIME NOT NULL,

  INDEX idx_version_id (version_id),
  INDEX idx_module (module_name),
  FOREIGN KEY (version_id) REFERENCES versions(id) ON DELETE CASCADE
);
```

### Table: `changelog_entries`

按 type 分组的展示内容，**不是**一条 commit 一条记录。

```sql
CREATE TABLE changelog_entries (
  id                CHAR(36) PRIMARY KEY,
  module_version_id CHAR(36) NOT NULL,                -- FK → module_versions.id
  type              ENUM('feature','bugfix','improvement','breaking','data_change','code_change') NOT NULL,
  message           TEXT NOT NULL,                     -- 已聚合的描述文本
  sort_order        INT DEFAULT 0,
  created_at        DATETIME NOT NULL,

  INDEX idx_module_version_id (module_version_id),
  INDEX idx_type (type),
  FOREIGN KEY (module_version_id) REFERENCES module_versions(id) ON DELETE CASCADE
);
```

### Table: `commit_records`

原始 git commit 记录，与展示分离。

```sql
CREATE TABLE commit_records (
  id                CHAR(36) PRIMARY KEY,
  module_version_id CHAR(36) NOT NULL,                -- FK → module_versions.id
  hash              VARCHAR(40) NOT NULL,
  short_hash        VARCHAR(9) NOT NULL,
  commit_url        VARCHAR(500),
  author            VARCHAR(100),
  message           TEXT NOT NULL,
  type              ENUM('feature','bugfix','improvement','breaking','data_change','code_change') NOT NULL,
  created_at        DATETIME NOT NULL,

  INDEX idx_module_version_id (module_version_id),
  FOREIGN KEY (module_version_id) REFERENCES module_versions(id) ON DELETE CASCADE
);
```

### Table: `releases`

各平台发布记录。

```sql
CREATE TABLE releases (
  id                CHAR(36) PRIMARY KEY,
  version_id        CHAR(36) NOT NULL,                -- FK → versions.id
  platform          ENUM('web','app','desktop','api') NOT NULL,
  status            ENUM('draft','releasing','released','rollback','archived') NOT NULL DEFAULT 'draft',
  package_url       VARCHAR(500),
  package_hash      VARCHAR(64),
  package_size      INT,
  incremental_url   VARCHAR(500),
  rollout_percent   TINYINT DEFAULT 100,
  min_version       VARCHAR(20),
  released_at       DATETIME,
  created_at        DATETIME NOT NULL,
  updated_at        DATETIME NOT NULL,

  INDEX idx_version_id (version_id),
  INDEX idx_platform (platform),
  FOREIGN KEY (version_id) REFERENCES versions(id) ON DELETE CASCADE
);
```

## Changelog + Version 生成机制

### Bump 规则

| Commit 类型 | 模块 Version Bump | Project Aggregate（仅统计 apps/root） |
|---|---|---|
| `BREAKING CHANGE` 或 `feat!:` | major | major |
| `feat:` | minor | minor（如有 major 则保持） |
| `fix:` / `perf:` | patch | patch（如有更高则不覆盖） |
| `refactor:` | patch | patch |
| `chore:` / `docs:` / `test:` / `style:` | 不 bump | 不 bump |
| scope 为 `docs` | 不 bump | 不 bump，仅记录 changelog |

### 三阶段流程

```
┌────────────────────────────────────────────────────────┐
│ Phase 1: Detect（预览，只读）                            │
│                                                        │
│ GET /versions/detect                                    │
│   → git log <last_released_hash>..HEAD                 │
│   → 解析 conventional commit，按 scope 分组             │
│   → 返回拟 bump 结果（不写任何东西）                     │
│                                                        │
│ Response: {                                            │
│   projectVersion, nextProjectVersion,                  │
│   modules: [{ moduleName, currentVersion,               │
│               nextVersion, bumpType, changes }],       │
│   totalCommits, since                                   │
│ }                                                      │
├────────────────────────────────────────────────────────┤
│ Phase 2: Generate（创建 draft，仅写 DB）                 │
│                                                        │
│ POST /versions/generate                                 │
│   → 同 Detect 逻辑                                     │
│   → 写入 versions（status: draft）                      │
│   → 写入 module_versions                                │
│   → 写入 changelog_entries（聚合后）                    │
│   → 写入 commit_records（原始）                         │
│   → ❌ 不修改 package.json                              │
│                                                        │
│ package.json 版本仅在 Release 阶段写入                   │
├────────────────────────────────────────────────────────┤
│ Phase 3: Release（正式发布，写入文件）                   │
│                                                        │
│ POST /versions/:id/release                              │
│   → 修改 versions.status → released                    │
│   → 修改所有关联 releases.status → released             │
│   → 写入各模块 package.json（仅此阶段改文件）            │
│   → 写入根目录 package.json                             │
│   → 创建 git tag                                       │
│   → 触发 npm publish（如属 packages）                    │
└────────────────────────────────────────────────────────┘
```

### 增量检测机制

```
每次 Generate 执行后：
  └── 将 HEAD 的 commit_short_hash 存入 versions 表

下次 Detect/Generate：
  └── 查询 DB 中最新 released 版本的 commit_short_hash
  └── git log <hash>..HEAD
  └── 空 → 返回无变更，不创建版本
```

### 示例

```bash
$ git log --oneline --no-decorate v0.1.0..HEAD
5e2d40622 feat(web-blog): 新增用户注册页面
832abb6bf fix(auth): 修复 OAuth 回调异常
f5e6d7c8b feat(honest)!: 重写中间件 API
a1b2c3d4e perf(platform-api): 优化查询缓存
```

**Detect 结果：**

| scope | 类别 | 当前版本 | bump | 下一版本 |
|-------|------|---------|------|---------|
| web-blog | app | 0.0.1 | minor | 0.1.0 |
| auth | package | 0.3.0 | patch | 0.3.1 |
| honest | package | 1.2.0 | major | 2.0.0 |
| platform-api | app | 0.5.0 | patch | 0.5.1 |

**Project version（只统计 apps/web-blog + apps/platform-api）：**
`0.1.0` → 最高 minor → **0.2.0**

**Changelog 结构：**

## 数据聚合逻辑

### Detech/Generate 阶段

```
git log <hash>..HEAD --format="%H %h %s %b"
  → 逐条解析
  → 提取 scope, type, message
  → 按 scope 分组

对每个 scope:
  ├── 确定 module_type (package/app/root)
  ├── 读取所属 package.json 的当前版本
  ├── 取最高 bump 类型
  ├── 计算 next_version
  └── 聚合 changelog:
        同 type 的多条 commit → 合并到一条 changelog_entry
        同时保留每条的 commit_record
```

### Changelog 聚合规则

例如，一个模块有 5 条 `feat` 和 2 条 `fix`：

```
commit_records (5 条原始记录):
  feat(web-blog): 新增注册页面
  feat(web-blog): 新增登录页面
  feat(web-blog): 新增忘记密码
  feat(web-blog): 新增个人中心
  feat(web-blog): 新增设置页面
  fix(web-blog): 修复样式
  fix(web-blog): 修复导航

changelog_entries (2 条聚合记录):
  feature: 新增注册/登录/忘记密码/个人中心/设置页面
  bugfix: 修复样式、导航问题
```

## API 端点

### 三阶段核心流程

| Method | Path | 阶段 | 行为 |
|--------|------|------|------|
| **GET** | **`/versions/detect`** | Detect | 只读预览，不写任何东西 |
| **POST** | **`/versions/generate`** | Generate | 创建 draft 版本（仅写 DB） |
| **POST** | **`/versions/:id/release`** | Release | 正式发布（写文件 + git tag） |

### 其他端点

| Method | Path | 用途 |
|--------|------|------|
| GET | `/versions/latest` | 获取最新版本 |
| GET | `/versions` | 分页列表 |
| GET | `/versions/:id` | 版本详情 |
| GET | `/versions/:id/modules` | 版本内各模块版本详情 |
| GET | `/versions/:id/changelog` | 结构化 changelog（聚合后） |
| GET | `/versions/:id/commits` | 原始 commit 列表 |
| GET | `/versions/:id/releases` | 各平台发布记录 |
| POST | `/versions/:id/releases` | 添加平台发布 |
| **GET** | **`/versions/check`** | 客户端升级检测 |
| POST | `/versions/:id/rollback` | 回滚到指定版本 |
| PUT | `/releases/:id/rollout` | 调整灰度比例 |
| PUT | `/releases/:id/status` | 修改发布状态 |

### GET /versions/check（客户端升级检测）

```
Request:
  query:
    platform: 'web' | 'app' | 'desktop' | 'api'
    currentVersion: string (semver)
    channel?: 'stable' | 'beta' | 'canary'

Response:
  hasUpdate: boolean
  latestVersion: string
  forceUpgrade: boolean
  downloadUrl: string | null
  releaseNotes: string
  rollout: number              -- 灰度比例 0-100
```

## 版本状态机

```
                   ┌─────────┐
                   │  draft  │
                   └────┬────┘
                        ↓
                   ┌──────────┐
                   │ reviewing │
                   └────┬─────┘
                        ↓
                   ┌──────────┐
                   │ approved  │
                   └────┬─────┘
                        ↓
                   ┌──────────┐
                   │ releasing │
                   └────┬─────┘
                        ↓
                   ┌──────────┐
              ┌─── │ released  │ ───┐
              │    └──────────┘     │
              ↓                     ↓
        ┌──────────┐         ┌──────────┐
        │ rollback │         │ archived │
        └────┬─────┘         └──────────┘
             │
             ↓ (重新发布)
        ┌──────────┐
        │  draft   │
        └──────────┘
```

| 状态 | 含义 |
|------|------|
| `draft` | 刚生成，未审核 |
| `reviewing` | 审核中 |
| `approved` | 审核通过，等待发布 |
| `releasing` | 正在发布中 |
| `released` | 已正式发布 |
| `rollback` | 已回滚，`rollback_version_id` 指向回滚目标 |
| `archived` | 归档，不再使用 |

## 版本回滚

```
版本链：
  v1.5.0 ──→ v1.6.0 ──→ v1.7.0
                          ↑ rollback
                          └── rollback_version_id = v1.5.0.id

查询回滚链：
  GET /versions/:id → 返回 rollback_version_id
  客户端可逐级追溯回滚历史
```

## 升级策略

| `force_upgrade` | `min_client_version` | 行为 |
|:---:|:---:|------|
| false | null | 用户可选升级 |
| true | null | 检测到新版即强制 |
| false | 1.0.0 | 当前版本 < 1.0.0 时强制，否则可选 |
| true | 1.0.0 | 当前版本 < 1.0.0 时强制，且每次弹窗 |

## 灰度发布

`releases.rollout_percent` 控制比例。客户端检测时根据渠道 + 随机数判断是否展示。

## 增量更新

`releases.incremental_url` 存储差异包。客户端优先尝试增量更新，失败则回退全量。

## 与 Changeset 的关系

| 维度 | Changeset | Version 模块 |
|------|-----------|-------------|
| 用途 | npm publish 工作流 | 业务版本 + changelog |
| 触发 | `pnpm changeset version` | `POST /versions/generate`（CI） |
| 数据源 | `.changeset/*.md` | `git log` + conventional commit |
| 写 `package.json` | ✅ | ✅ **仅在 Release 阶段** |
| npm publish | ✅ | ❌ |
| changelog | markdown | 数据库（结构化） |

两者独立运行，互不干扰。
